规则定了哪些（docs/engineering-contract.md）

  1. 门槛 — typecheck / lint / test 三条，必须原样跑、不许接管道（接了 | tail 会把红灯读成绿灯）。
  2. 依赖方向单向 — app/ 只是边界适配器（解析请求 → 调 lib → 塑形响应，不放业务）；lib/ framework-free；components/ 可以引 lib，反向不行；bin/ 只管语法，行为都在 lib/cli.ts。
  3. 文件纪律 — 单文件 300 行硬上限；一个文件一个概念；不允许"只为缩短 import 路径"的转发层；测试与代码同目录，测试专用工具放 test/。
  4. 出站面只过 plain data — JSON、SSE、CLI stdout、server component 传给 client 的 props；Effect 不出服务端，浏览器 bundle 里零 Effect。
  5. Effect 代码禁 try/catch — Effect.try / tagged error / catchTag / ensuring / acquireUseRelease；进程最外层例外，转成 exit code 或 wire error。
  6. 死代码政策 — 无未用导出、无注释掉的代码、无"以防万一"的 flag；唯一例外是 lib/features.ts 里带理由和复活条件的正式开关。
  7. 渲染路径红线 — 渲染循环里不许有 per-node 同步 IO；贵插件按内容开关；改渲染必须给前后基准数。
  8. 公开仓库卫生 — 源码/注释/提交信息里不出现内部卡号、私有主机名、本机绝对路径、密钥。

为什么规则不在 AGENTS.md

追加 · admin · 17:14:55

Effect 改造：只做边界，一次一刀

三个文件，107 行，全部在 lib/effect/

  • errors.ts（55 行）— tagged failure 联合：SessionNotFound / CommentNotFound / ReplyNotFound / InvalidInput / LockTimeout / IoFailure / GitFailure / ImageRejected。每个都带今天线上就在用的 status 和 error 字符串，所以"失败 → 响应"是机械映射，措辞不变。
  • runtime.ts（19 行）— 全进程一个 ManagedRuntime，globalThis 缓存（dev HMR 每次热更都会重新求值模块，不缓存就每次泄漏一个 fiber scope）。本轮 Layer 故意为空：仓库还是普通函数，没有服务要 provide。不做 per-request runtime。
  • respond.ts（33 行）— respond(effect, status) / respondRaw(effect)：跑程序，失败回 {error} + status，成功回 body，defect 回 500。全仓库只允许这里调 runPromise。

9 个 route handler 全部变成一行 return respond(program(req))

  • comments 不再有 json() 的 try/catch，也不再有 /not found/ → 404 的 catch，改成 typed tag。
  • asset 的 stat try/catch、watch 的三处 try/catch（enqueue / fs.watch / close）全部消失。

怎么证明"线上没变"

  • test/wire-snapshot.test.ts：9 个 handler × 45 个用例，记录 {status, contentType, headers, body}。先用改造前的代码生成并单独提交，重构提交之后这个文件 diff 为空。
  • 四条 rg 门槛，真实输出：app/api+lib/effect 的 try {/catch ( 为空；components 里没有 from "effect"；产物 chunk 里没有 ManagedRuntime|TaggedError；runPromise 只出现在 respond.ts。
  • 结论：测试数 391 → 384（#32 删掉 7 个属于被删模块的测试）→ 385（#33 新增一个快照测试）。
