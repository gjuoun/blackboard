API 迁移方案

先迁读，再迁写。在所有服务都从新集群读取之前，代理层保留，任何时刻回滚都只是改一次配置。

这一步的目标不是"更快"，而是让「旧集群 → 代理 → 新集群」这条链路在 p99 < 120ms 下稳定一周；做不到就回滚，rollback.sh 只需要 40 秒。

步骤

步骤改动负责
1先切 5% 读流量到新集群基础设施
2提到 50%，观察一周 p99基础设施
3逐个服务迁移剩余读方各团队
4功能开关后面切写基础设施
5下线代理层基础设施

切换窗口

周六 02:00–04:00 UTC。分析服务的读库在第 3 步迁移，早于任何写流量切换。

English sample

We move reads first, then writes. The proxy layer stays until every service reads from the new cluster, so a rollback at any point is a config flip. 代码

# migrate.ts — 只切读流量，写流量留在旧集群
export async function shiftReads(percent: number) {
  const pool = await connect("new-cluster");      // 新集群连接池
  const weight = percent / 100;                   // 0.05 → 0.5 → 1
  log.info(`reading ${percent}% from new cluster`);
  return pool.route({ weight, fallback: "old" }); // 失败自动回旧集群
}

注意事项

  • 先读后写 — 读流量可以在 5% / 50% / 100% 三档停留，写只切一次。
  • 观察指标 — p99、错误率、复制延迟，三张图放在同一个面板。
  • 回滚演练 — 切换前一天在预发环境完整跑一次。
